# Спецификация приложения: MetroCheck — система контроля протоколов поверки

## 1. Назначение

Автоматизированная проверка наличия и содержания протоколов поверки, оформленных метрологической лабораторией ООО «МКАИР». Замещает ручной труд исполнительного директора по ежемесячному контролю качества протоколов.

## 3. 8-фазный пайплайн проверки

```
public_api → protocol_scan → protocol_ocr → data_extract →
partial_check → wait_token → lk_api → full_check → report
```

Фазы 1-5 **не требуют токена** АРШИН ЛК (работают с публичным API и локальными файлами).
Фазы 7-8 **требуют токен** (запросы к ЛК АРШИН через Synology Drive).

### Фаза 1: public_api
Загрузка поверок из публичного API АРШИН (`fgis.gost.ru/fundmetrology/eapi/vri`) за указанный месяц. Фильтр по `org_title=ООО "МКАИР"`. Результат сохраняется в таблицу `calibrations`.

### Фаза 2: protocol_scan
Сканирование директории `/protocols/{year}.{month}/` — рекурсивный поиск PDF-файлов. Регистрация найденных файлов в таблицу `protocol_files`. Подсчёт SHA256 для дедупликации.

### Фаза 3: protocol_ocr
Извлечение текста из каждого PDF через Tesseract OCR (с русским языком). Таймаут 30 сек на файл. Результат сохраняется в `protocol_files.raw_text`.

### Фаза 4: data_extract
Извлечение структурированных данных из OCR-текста:
- **Основной метод:** регулярные выражения (без AI, $0)
- **Fallback:** OpenRouter AI (все бесплатные модели: `kimi-k2.6:free`, `gemma-4-31b-it:free`, `qwen-qwq-32b:free`…)
- **Извлекаемые поля:** номер протокола, тип СИ, заводской номер, владелец, поверитель, дата поверки, диапазон измерений, метод поверки, условия (t°, влажность, давление), результат
- **Логика fallback:** AI вызывается для ЛЮБОГО поля, если regex не дал результата (до этого было только 3 поля при confidence<0.5). Все AI-вызовы логируются с префиксом `AI_FALLBACK` — видно: файл, какие поля заполнил AI, и кусок OCR-текста вокруг метки поля. По этим логам человек может добавить новые regex-паттерны.

Извлечённые данные сохраняются в `protocol_data`.

### Фаза 5: partial_check
Сравнение извлечённых данных с публичным API АРШИН:
- **Полнота:** все ли поверки из АРШИН имеют протокол?
- **Наличие:** все ли протоколы имеют запись в АРШИН?
- **Соответствие:** совпадают ли поверитель, дата, результаты?

### Фаза 6: wait_token
Ожидание валидного токена АРШИН ЛК. Токен поступает через Synology Drive:
1. Зонов логинится на `fgis.gost.ru` → Chrome Extension ловит JWT
2. Extension пишет токен в `SynologyDrive/tokens/arshin-token.json`
3. Synology Drive синхронизирует файл на NAS → на сервер
4. Backend мониторит файл `/shared/tokens/arshin-token.json`

### Фаза 7: lk_api
Загрузка детальных данных из ЛК АРШИН (с Bearer-токеном):
- Детали поверок (`fetch-lk-details`)
- Дополнительные данные (`fetch-data2`)
Результат обогащает записи в `calibrations`.

### Фаза 8: full_check
Полная проверка с учётом данных из ЛК:
- Сверка всех полей: тип СИ, поверитель, диапазон, даты, условия
- Формирование отчёта (Excel) и отправка email

- **Стек:** `docker-compose.yml` (порты 8xxx)
- **БД:** `mkair` (production)
- **Ожидание:** 5 минут (проверка staging перед production)

## 6. Токен АРШИН ЛК

### Жизненный цикл

```
Зонов в Chrome → fgis.gost.ru → логин через Госуслуги
  → SPA сохраняет JWT в localStorage
  → Chrome Extension (content.js) каждые 3 сек проверяет localStorage
  → Находит значение eyJ... → background.js → пишет в файл
  → Synology Drive Client (Windows) синхронизирует на NAS
  → Synology Drive Client (Linux, сервер) синхронизирует на сервер
  → /home/mflkee/SynologyDrive/tokens/arshin-token.json
  → смонтировано в контейнер как /shared/tokens/arshin-token.json
  → Backend читает файл, обновляет токен в памяти
  → Использует для LK запросов, архивирует использованные токены в .used
```

### Важно
- Токен живёт ~1 час
- Для обновления требуется ручной вход Зонова в ЛК АРШИН
- Job ставится на паузу (фаза `wait_token`) до появления свежего токена
- После потери токена mid-check — job автоматически возобновляется после получения нового

## 7. Извлечение данных (data_extract)

### Regex (основной метод)
Извлечение полей из OCR-текста через регулярные выражения:
- `serial_number` — поддержка кириллицы, пробелов, разных форматов
- `device_name`/`device_type` — разделение по `;`, склейка многострочных названий, нормализация единиц. Учёт числовых префиксов (`6. `) и альтернативных формулировок (`Наименование нормативного документа по поверке`)
- `verification_method` — поиск блоков с `Методика поверки:`, `МИ ...`, `МП ...`, `ГОСТ ...`, `Наименование нормативного документа по поверке`
- `measurement_range` — извлечение из таблиц через pdfplumber `extract_tables()` + fallback regex
- `verifier` — ФИО поверителя
- `owner` — владелец СИ (спаршивается `Принадлежность`, `Владелец`, `Организация`, `Принадлежащее`)
- `manufacture_year` — ищет `Год выпуска`, `Дата выпуска`, `Год изготовления`

### AI (fallback)
- OpenRouter, каскад бесплатных моделей (chain), начиная с `kimi-k2.6:free`, `nemotron-3-super-120b:free`
- Вызывается для **ЛЮБОГО** поля, если все regex-паттерны не дали результата (раньше: только 3 поля при confidence<0.5)
- Использует полный системный промпт AIExtractionService (все поля в одном запросе)
- Результаты логируются с префиксом `AI_FALLBACK`:
  ```
  AI_FALLBACK file=2025.12.19 № ER230201049 (МПИ-3).pdf 
  fields={'owner': 'ООО "Газпром"'} 
  snippet=[owner]...5. Принадлежность: ООО "Газпром"↵6. Наименование...
  ```
- Rate limit (429 для free моделей ~2 запроса/мин) — основная проблема, поэтому regex является primary методом
- **Процесс:** `grep AI_FALLBACK` в логах → анализ контекста → добавление нового regex-паттерна в соответствующий `_extract_*`

## 9. Безопасность

- API-key (`x-api-key`) для всех эндпоинтов (проверка через `FASTAPI_API_KEY`)
- JWT-токен АРШИН хранится в файле, доступном только из контейнера
- OpenRouter API key — в env-переменной контейнера
- PostgreSQL — только localhost
- Netbird VPN — P2P mesh без открытых портов
